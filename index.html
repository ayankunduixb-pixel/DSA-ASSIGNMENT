OSS Graveyard / Guide
Student Competition · Two Tracks · 12-hour window

⚰️  A student challenge in two tracks

Explore open source. Understand the work. Bring ideas back to life.

Open source is not just about GitHub, coding, or making Pull Requests. Behind every open-source project is a problem someone wanted to solve, a solution someone built, and a community that decided to share and improve it.

But what happens when that community disappears? And what happens when a project is still alive, but has a problem that nobody has fixed yet? OSS Graveyard gives you both questions to explore.

01What is it

OSS Graveyard is a competition where you explore real open-source projects and investigate how they are built, maintained, contributed to, and sometimes abandoned.

There are two completely independent tracks. You may participate in only one.

02Track A ⚰️

Postmortem

Find something that died. Understand why. Decide whether it deserves another life.

You will find an open-source project that is no longer meaningfully maintained and perform a technical and community postmortem. You are essentially acting like an investigator.

Your job is not to say

“This repository has not been updated for two years.”

Your job is to answer

“What happened to this project, why did it fail, is the original problem still relevant, and would reviving it actually create value?”

What “dead” means

A project does not have to be officially labelled Archived. It may be considered inactive if there is credible evidence such as:

  • No meaningful development for a long period
  • Maintainers have stopped responding
  • Important issues remain unresolved
  • Pull Requests have been abandoned
  • Dependencies are severely outdated
  • Releases have stopped
  • Community activity has disappeared
  • Users have moved to alternatives
  • The technology has become obsolete

You must show evidence rather than simply assume that the project is dead.

03Track A mission

Your investigation should follow this journey.

PROBLEM→PROJECT→COMMUNITY→DECLINE→POSTMORTEM→TODAY→VERDICT

A1Original problem

Understand why the project existed

QuestionWhat to find
What problem?The real-world problem being solved
Who had the problem?Target users
Why did it matter?Importance and use case
What was the solution?How the project solved it
Why open source?Why sharing and community made sense
A2The project

Explore the project's history

Repository·README·Commit history·Releases·Contributors·Issues·Pull Requests·Discussions·Documentation·Dependencies·Community channels

Try to reconstruct the project's journey, then ask:

How did it start?→What happened during its active period?→When did activity decline?→What changed?

A3The people

Open source is not simply “people writing code for free”

People contribute because they receive value in different forms.

Learning→Experience→Reputation→Community→Impact→Career→Personal use

  • Who contributed?
  • What kind of contributions were made?
  • Why might people have contributed?
  • Was there a healthy contributor community?
  • Was the project dependent on one or a few maintainers?
A4The postmortem

Now determine why the project died

You may discover one reason or several.

Possible causeWhat to investigate
Maintainer inactivityDid key maintainers stop contributing?
Contributor shortageDid the project fail to attract contributors?
Technical debtDid the code become difficult to maintain?
DependenciesDid external dependencies break or become outdated?
Better alternativesDid another project replace it?
User declineDid people stop using it?
Technology changeDid the underlying technology become obsolete?
DocumentationDid poor documentation make contribution difficult?
CommunityDid the community disappear?
Problem changedDid the original problem become irrelevant?

Important — separate what you know from what you infer

Evidence“The last commit was in 2021.”
Inference“The maintainer lost interest.” — unless supported by evidence.

Good postmortems make this distinction clear.

A5Still alive?

The project may be dead while the problem is still alive

This is where your investigation goes beyond GitHub. Research the current landscape and find out:

  • Does the original problem still exist?
  • Who faces it today?
  • How is it currently solved?
  • Are there better alternatives?
  • Has the problem changed?
  • Is there still an unmet need?
A6The verdict

At the end, you must make a decision

🪦
Let it rest

The project should remain in the graveyard.

Explain why.

⚡
Give it a second life

The project or its underlying idea deserves another chance.

  • Who needs it today
  • Why the problem remains relevant
  • What needs to change
  • What you would do first
  • What the new project or community could look like
  • Why contributors would care today

You do not have to actually revive the project. Your job is to make a strong, evidence-backed decision.

05Track B 🔧

Contribution

Pick an open-source project. Understand how it works. Find a real issue. Try to fix it.

Unlike Track A, your project does not have to be dead, abandoned, or inactive. You can choose a project that is actively maintained and has an issue you believe you can work on.

The goal is to give you your first real experience of understanding and contributing to an open-source codebase.

B1Pick a project

Choose a project that

  • Is genuinely open source
  • Has a public repository
  • Has an understandable codebase
  • Has open issues
  • Is suitable for your current skill level

It can be from any domain or technology.

AI·Web·Cybersecurity·Developer Tools·Education·Healthcare·Climate·Robotics·Data Science·Accessibility·Mobile·Hardware

B2Find an issue

Look for something you can realistically understand and attempt to solve

  • A bug
  • Missing functionality
  • Performance
  • Documentation
  • Testing
  • Developer tooling
  • UI / UX
  • Configuration
  • Security
  • Other meaningful improvements

Do not immediately start coding. First understand the project.

B3Architecture — mandatory

You must create an architecture diagram yourself

This is one of the most important requirements of Track B. Your diagram should show the major parts of the system and how they communicate. Depending on the project, this may include:

ComponentExample
Entry pointCLI / API / Application
FrontendWeb or mobile interface
BackendServer / services
Core logicMain processing modules
DatabaseStorage layer
APIsInternal and external APIs
External servicesThird-party services
DependenciesMajor libraries and frameworks
Data flowHow information moves
TestingUnit and integration tests
DeploymentBuild and deployment pipeline

Your diagram should answer

“If I joined this project tomorrow, could I understand how the system works from this diagram?”

Do not simply copy an existing architecture diagram. It must reflect your understanding of the actual codebase.

B4Understand the issue

Your analysis should answer

QuestionWhat to explain
What is the issue?Problem description
Where is it?File / module / component
What causes it?Root cause
Who is affected?Impact
What should happen?Expected behaviour
What happens now?Current behaviour
What will you change?Proposed solution

Your reasoning should connect:

ARCHITECTURE→ISSUE→ROOT CAUSE→SOLUTION

B5Try to fix it

Now implement your solution

  • Writing code
  • Fixing a bug
  • Adding tests
  • Improving documentation
  • Improving performance
  • Fixing UI / UX
  • Improving developer tooling
  • Improving configuration
  • Another meaningful improvement

If appropriate, create a Pull Request on the original repository.

Does the PR have to be merged?

No. A merged PR is not mandatory. We care about whether you:

understood the problem→found the right place→proposed a sensible solution→implemented it→tested it

07How do I find a project?

Don't overthink the first step.

Tip 1 — Start with your interestsPick two domains you like and search for projects at their intersection. Example: AI + Healthcare → medical AI tools, clinical NLP, healthcare analytics.
Tip 2 — Generate keywordsAsk an AI assistant: “Give me GitHub search keywords for open-source projects at the intersection of AI and healthcare.” Use those keywords to search.
Tip 3 — Explore OSS organizationsBrowse projects from organizations and communities such as FOSSASIA and find something interesting.
Tip 4 — Read before choosingCheck the README, issues, commits, contributors and recent activity before committing to a project.

15Originality & AI use

AI tools are allowed as assistive tools.

You may use them for generating search keywords, understanding unfamiliar concepts, brainstorming, research assistance, debugging, explaining code and suggesting possible approaches.

AI should assist your work, not replace your understanding.

In Track BDo not submit an AI-generated architecture diagram that you cannot explain.
In Track AVerify information instead of blindly accepting an AI-generated explanation of why a project died.

You are responsible for everything you submit.

17Common mistakes

⚰️ Track A — don't

  • Pick a repository just because it is old
  • Assume inactivity without evidence
  • Focus only on GitHub commits
  • Ignore the original users and problem
  • Assume revival is always the right answer
  • Make claims without sources

🔧 Track B — don't

  • Pick an issue without understanding the project
  • Copy an existing solution
  • Copy the project's architecture diagram
  • Make changes without understanding the module
  • Submit untested code
  • Assume a PR must be merged

20The point

You don't need to know everything about open source before entering. You just need to be willing to look deeper than the surface.

A repository is more than a collection of files.

It has a problem behind it.

It has people behind it.

It has a community behind it.

It has a history.

And sometimes, it has an opportunity waiting for someone to pick it up again.
